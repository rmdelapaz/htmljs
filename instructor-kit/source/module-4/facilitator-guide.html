Module 4 — The DOM

How to teach the four lessons where JavaScript finally touches the page: the document tree, selecting and changing elements, responding to events, and building elements from scratch. Timing, live-demo scripts, the misconceptions to pre-empt, and how to run each lab.

4 lessons ~3.3 hrs teaching Lessons L13–L16 Level Intermediate Maps to Day 3 PM (L13–L14) → Day 4 AM

How to Use This Guide

  • Each lesson has the same rhythm: Frame (why it matters) → Teach (live-code the concept) → Lab (students build) → Check (quiz + recap) → Journal. The minute timings in each teaching sequence add up to the lesson's length; adjust ±10 min to your group. Close each lesson with 3–4 minutes for the lesson's Learning Journal prompt (in the lesson and the workbook).
  • Live-code everything, with the console open. Split the projector: editor on the left, browser + DevTools on the right. Every DOM change should be something students see happen, and every error something they see you read and fix.
  • Blue blocks are concepts; teal blocks are hands-on; amber blocks are watch-outs — the errors that eat class time if you don't pre-empt them.
  • Quiz answers here are for you. The student workbook has a 3-question subset of each lesson quiz, without answers, labelled with the lesson's question numbers; the separate Answer Key covers every question with matching numbers for grading.
Before you start the module

Students need VS Code with Live Server, a browser with DevTools, and comfort with functions, arrays, objects and template literals from Modules 1–3. Open labs/module-4/ and check each starter/ folder opens with Live Server on your machine. From this module on, every lab is a real page: an index.html that loads script.js at the end of <body>. If anyone's script "does nothing," check the <script src> path and the Console before anything else.

Lesson Plans

L13

Introduction to the DOM

45 min
Objectives
  • Explain what the DOM is and why JavaScript works on it, not on the HTML file
  • Describe how the browser builds the document tree; identify window, document, elements and nodes
  • Navigate with parentElement, children, and the *ElementSibling properties
  • Inspect the live DOM in DevTools and tell it apart from View Source
Teaching sequence
  1. Frame (4m). "Everything you've written so far only talked to the console. Today JavaScript touches the page." Give the lesson's analogy: HTML is the blueprint, the DOM is the building, JavaScript is the contractor who remodels it after it's built.
  2. Draw the tree (7m). Put the lesson's small HTML page on screen and draw its tree on the board (or show the diagram below). Name parent, child, sibling, text node on the drawing. Point at the dashed whitespace node — it's the reason for the watch-out later.
  3. Key objects & node types (6m). In the console: window.innerWidth, document.title, document.body. Then h1.nodeType (1) vs h1.firstChild.nodeType (3). "document is your front door to the page."
  4. Traversing (8m). Live-walk a list: 
    const list = document.querySelector("ul");
list.children;            // HTMLCollection of <li>
list.firstElementChild;   // the first <li>
list.firstChild;          // #text "\n  " — surprise!
list.children[1].nextElementSibling;
    Let the firstChild surprise land, then show the Element-vs-Node table: "use the Element versions."
  5. DevTools & source vs live DOM (5m). Change the h1 in the console, then open View Source (Ctrl + U): unchanged. Open Elements: changed. Show $0.
  6. Lab (8m). DOM Explorer — see below.
  7. Check (3m). Quiz Q1–Q5 as a quick poll.
  8. Journal (4m). The lesson's prompt: sketch a DOM tree of one of their own pages.
Live-demo script
  1. Open labs/module-4/l13-dom-explorer/starter/index.html with Live Server, F12, Console. Type document.body.children and expand it: "five element children — count them in the HTML."
  2. Type document.querySelector("#family").firstChild. Read the output aloud: "#text". Ask the room why. Then .firstElementChild.
  3. Set document.querySelector("h1").textContent = "Changed!", then Ctrl + U. "The file didn't change. The DOM did." Refresh to undo.
Lab — DOM Explorer

In the lesson, students explore the lesson page itself. For class, use the practice page in labs/module-4/l13-dom-explorer/starter/: its README.md is the worksheet (the lesson's 10 console tasks + 3 "think about it" questions). The solution in labs/module-4/l13-dom-explorer/solution/ runs every task and prints the results on the page and in the console — project it for the debrief.

Circulate for: typing into the Console (not the Elements search box); forgetting the . in ".lesson-section"; students who can't find <main> at children[3] — have them count <body>'s element children aloud.

Watch-outs
  • Whitespace text nodes. firstChild, childNodes and nextSibling include the line breaks between tags. Beginners assume firstChild is the first tag. Rule: if you want an element, use the property with "Element" in its name.
  • "I edited the DOM, why didn't my file change?" Console and Elements-panel edits live in memory only. Refresh throws them away. Real changes go in the .js file.
  • Script in <head> without defer → document.querySelector returns null because the body hasn't been parsed yet. Keep scripts at the end of <body> (or use defer).
  • children is a live HTMLCollection, not an array — it has length and indexes but no forEach. Plant the seed; L14 contrasts it with the static NodeList.
Check for understanding

Key answers: the DOM is B — an in-memory tree of objects; entry point = B — document; parentElement = B — the element that contains this one; a JS-added <p> shows in C — the Elements panel (not View Source); list.firstChild isn't the <li> because D — the whitespace before it is a text node.

L14

Selecting & Modifying Elements

50 min
Objectives
  • Select with querySelector, getElementById and querySelectorAll
  • Change text safely with textContent; know when innerHTML is dangerous
  • Add, remove and toggle classes with classList; set inline styles with style
  • Read and write attributes and data-* values with dataset
Teaching sequence
  1. Frame (3m). "Last lesson we looked. Now we grab and change." Hook: "If you know CSS selectors, you already know how to find elements."
  2. Selecting one (7m). querySelector("h1"), (".card"), ("#main-nav"), an attribute selector. Then a typo'd selector → null. Then null.textContent → the famous "Cannot read properties of null". Read that error together.
  3. Selecting many (6m). querySelectorAll returns a NodeList: forEach works, map doesn't. Spread it: [...items].map(...). Show that it's a snapshot: add an <li>, the old NodeList's length doesn't change; list.children.length does.
  4. Text & the XSS talk (8m). textContent = "<em>Not italic</em>" shows the tags literally. Then the lesson's attack string in innerHTML: 
    const userInput = '<img src="x" onerror="alert(\'hacked!\')">';
box.innerHTML = userInput;    // ❌ the alert fires
box.textContent = userInput;  // ✅ harmless text
    Stress: a <script> tag inserted with innerHTML does not run — it's the onerror attribute that does. That's why "it didn't run my script tag" is not proof of safety.
  5. classList (5m). add, remove, toggle, contains. Then card.className = "active" and watch the card class vanish.
  6. Inline styles (4m). camelCase (backgroundColor). Show h1.style.fontSize → "", then getComputedStyle(h1).fontSize → "32px". Land the rule: prefer classes over inline styles.
  7. Attributes & dataset (4m). getAttribute("href") vs link.href (resolved URL). data-item-id → dataset.itemId; values are always strings.
  8. Lab (8m). Profile Card Editor.
  9. Check (2m). Quiz Q1–Q5.
  10. Journal (3m). End of Day 3 — give the full time.
Live-demo script
  1. Open labs/module-4/l14-profile-card/starter/. In script.js, do task 6 (card.style.backgroundColor = "#eff6ff"), save, then click Toggle dark mode. The text goes light but the card stays light blue — unreadable.
  2. Ask "why?" Inspect the card: the style="…" attribute beats the .dark class. Add card.style.backgroundColor = "" before the toggle, save, click again. Fixed.
  3. Say it: "Inline styles win the cascade. Toggle classes for looks; use style only for truly dynamic values."
Lab — Dynamic Profile Card Editor

The lesson's profile.html, split into index.html + style.css + script.js. Students complete TODOs 1–9 and the updateProfile() bonus. Starter in labs/module-4/l14-profile-card/starter/ (button listeners provided — events are next lesson); solution in labs/module-4/l14-profile-card/solution/.

Circulate for: dataset.user-id (a subtraction, not a property!); setting href but not the link text (task 4 needs both); the bonus using destructuring { name, bio, location, website } in the parameter list.

Watch-outs
  • innerHTML with user text = XSS. Demo with <img src=x onerror=…>, never with <script> (it won't run and students conclude "it's safe"). "User input" includes form fields, URL parameters, API data, localStorage.
  • innerHTML += rebuilds everything inside the container — listeners are wiped and typed input values are lost. L16 shows the better way.
  • element.style reads only inline styles. Reading .style.color to "check the current color" returns "" for anything set in the stylesheet. Use getComputedStyle.
  • Static NodeList vs live HTMLCollection. querySelectorAll is a snapshot; children updates itself. Re-query after adding elements.
  • null from a wrong selector. Missing # or . is the usual cause; the error appears one line later, where the property is read.
Check for understanding

Key answers: no match → C — null; avoid innerHTML with user input because B — it can execute malicious scripts (XSS); add a class safely = A — classList.add; data-item-id → B — dataset.itemId; stylesheet-only font size → style.fontSize is D — "" (empty string).

L15

Events & Event Listeners

55 min
Objectives
  • Attach listeners with addEventListener for click, input, submit and keydown
  • Use the event object: target, currentTarget, key
  • Cancel default behavior with preventDefault(); explain capturing and bubbling
  • Delegate events from a parent with closest(); remove listeners correctly
Teaching sequence
  1. Frame (3m). Open Day 4 with a 60-second recap of selecting and modifying. Then the doorbell analogy: the event is someone pressing the bell; the listener is what you decide to do when it rings.
  2. addEventListener (5m). One button, one listener. Then the classic bug live: addEventListener("click", handleClick()) — it runs once on load and never again. "Pass the function; don't call it."
  3. Event types & the event object (7m). input on a text box (every keystroke) vs change (on commit); keydown logging event.key. Log event.target and event.currentTarget on a card containing a button.
  4. preventDefault (5m). A form without it: the page reloads and the console clears. Add event.preventDefault() — it stays. Tick the Console's "Preserve log" to show the reload happening.
  5. Propagation (8m). The lesson's outer/inner/button example. Ask the room to predict the log order before clicking (that's also the journal prompt). Then add a capture listener on #outer and watch it jump to first. Use the diagram below.
  6. Delegation (8m). One listener on the list, event.target.closest(".delete-btn"). Add a new button after the fact — it just works. Then show why matches() fails when the click lands on an icon <span> inside the button.
  7. Removing listeners (4m). Named function in, same named function out. { once: true }. Mention AbortController as "good to know."
  8. Lab (10m). Interactive Task List.
  9. Check (2m). Quiz Q1–Q6.
  10. Journal (3m).
Live-demo script
  1. Paste the lesson's three nested listeners into a blank page. "Before I click — what prints first?" Take three guesses, then click: Button, Inner div, Outer div.
  2. Add event.stopPropagation() in the button listener, click: only "Button." Remove it again and say why: "It breaks delegation. Prefer checking event.target."
  3. Open labs/module-4/l15-task-list/solution/, add a task, then type <img src=x onerror=alert(1)> as a task. It shows as plain text: "That's why we use textContent for anything a user typed."
Lab — Interactive Task List

The lesson's tasks.html as index.html + style.css + script.js. Students handle submit with preventDefault(), build each <li> (fixed markup via innerHTML, the user's text via textContent), delegate complete/delete with closest(), and write updateCounter(). Bonus: Escape clears the input; "d" toggles body.dark-mode. Files in labs/module-4/l15-task-list/.

Circulate for: listeners attached to each new button inside the submit handler (works, but misses the point — steer to delegation); counters that don't update after delete; the emoji buttons keeping their aria-labels ("Mark done", "Delete task") so screen readers announce them.

Watch-outs
  • Calling instead of passing: handleClick() vs handleClick. The most common event bug of the day.
  • removeEventListener needs the same function reference. A new arrow function that looks identical is a different object, so nothing is removed and there's no error.
  • focus, blur, mouseenter, mouseleave don't bubble, so delegating them from a parent silently does nothing. Use focusin/focusout or mouseover/mouseout.
  • target vs currentTarget. With delegation, target may be a child (an icon, a <span>). That's why closest() beats matches().
  • Document-level shortcuts fire while typing. The "d" shortcut must check that the input isn't focused, or every "d" in a task name toggles dark mode.
Check for understanding

Key answers: addEventListener takes B — an event type string and a callback; event.target = B — the element actually interacted with; preventDefault() C — cancels the browser's built-in behavior; delegation's advantage = C — one listener for current and future children; fire once = B — addEventListener("click", handler, { once: true }); icon-span fix = A — event.target.closest(".delete-btn").

L16

Creating & Removing Elements

50 min
Objectives
  • Create and configure elements with createElement before inserting them
  • Insert with append, prepend, before, after; remove with remove(), replaceWith(), replaceChildren()
  • Copy elements with cloneNode(true) and the <template> element
  • Choose between innerHTML and createElement; batch inserts with a DocumentFragment
Teaching sequence
  1. Frame (3m). "So far we changed elements that were already there. Now we build new ones." Show the lesson's four-step flow: create → configure → add children → insert.
  2. createElement (6m). Create a <p> in the console, log it, point out it's not on the page. Configure it (text, class, dataset), then document.body.append(p) — now it appears.
  3. Inserting (7m). On a numbered list: append, prepend, before, after. Then append an existing item somewhere else — it moves. "One element, one place."
  4. Removing & clearing (5m). el.remove(), replaceWith(), and list.replaceChildren() to empty a container. Mention removeChild only as "what you'll see in old tutorials."
  5. Cloning (5m). cloneNode(false) vs cloneNode(true); a quick <template> + template.content.cloneNode(true). Note: clones don't copy addEventListener listeners — another reason to delegate.
  6. innerHTML vs createElement (5m). Walk the lesson's comparison table. Demo the innerHTML += trap: type into an input inside a container, run container.innerHTML += "<p>hi</p>" — the typed text is gone.
  7. DocumentFragment (4m). Build 100 items in a fragment, append once, then log fragment.childNodes.length → 0. "The fragment is a shopping bag; you empty it onto the page."
  8. Lab (10m). Notification System.
  9. Check (2m). Quiz Q1–Q5.
  10. Journal (3m). This prompt also asks them to look back over the whole module.
Live-demo script
  1. In the console: const p = document.createElement("p"); p → <p></p>. "Where is it on the page?" Nowhere. p.textContent = "Hi!"; document.body.append(p).
  2. Run document.body.append(p) a second time. "Did we get two?" No — it moved to the same spot. document.body.append(p.cloneNode(true)) — now two.
  3. Open labs/module-4/l16-notifications/solution/, click a few buttons, press b for the batch, then Clear All. Point at aria-live="polite" on the area: "screen readers announce each new toast."
Lab — Dynamic Notification System

The lesson's notifications.html as index.html + style.css + script.js. Students write showNotification(type, message) with createElement + textContent, delegate the controls and the close buttons with closest(), clear with replaceChildren(), auto-remove after 5 seconds, and count with updateCount(). Bonus: the "b" key adds five at once through a DocumentFragment. Files in labs/module-4/l16-notifications/.

Circulate for: the close button missing aria-label="Dismiss notification"; the count not updating after the auto-remove timer; students trying Ctrl + Shift + N for the bonus — Chrome reserves it (new incognito window) and the page never sees the key. That's why the lesson uses "b".

Watch-outs
  • "I created it but I can't see it." They forgot to insert it. createElement only builds it in memory.
  • Appending moves, it doesn't copy. Looping list.append(sameItem) five times gives one item. Create a new element (or clone) each time.
  • Building with innerHTML += in a loop — slow, wipes listeners, and an XSS hole if the text came from a user. createElement + textContent + append instead.
  • The fragment is empty after insertion. Students who try to reuse it get nothing the second time. Build a new fragment per batch.
Check for understanding

Key answers: createElement("div") returns B — a new <div> in memory, not yet in the DOM; appending an existing element B — moves it; modern removal = C — element.remove(); cloneNode(true) vs false = A — deep vs shallow; DocumentFragment C — batches many insertions into one DOM update.

Closing the Module

Module 4 wrap-up (10 min)

Have two or three students demo their task list or notification system on the projector, and ask each to point at one line that uses delegation and one that uses textContent for user text. Recap the arc: see the tree → grab and change → respond to users → build and remove. Preview Module 5: "You now have the full DOM toolkit. Next we put it to work on real features — forms with validation, timers, saving data, and live data from APIs."
