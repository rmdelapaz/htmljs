Module 5 — Building Interactive Pages

How to teach the four lessons where students stop writing exercises and start building real features: a validated sign-up form, a Pomodoro timer, a to-do list that survives a refresh, and a live GitHub search. This guide covers timing, live-demo scripts, the async misconceptions to deal with early, and how to run each lab.

4 lessons ~3.5 hrs teaching Lessons L17–L20 Level Intermediate Maps to Day 4 PM (L17–L18) → Day 5 AM

How to Use This Guide

  • Each lesson follows the same rhythm: Frame (why it matters), Teach (live-code the concept), Lab (students build), then Check (quiz and recap). The minute timings add up to the lesson's length. Adjust by ±10 min for your group. End each lesson with 3–5 minutes on the lesson's Learning Journal prompt, which appears in the lesson and in the workbook.
  • Live-code everything, with the Console and the relevant DevTools panel open: Elements for forms, Application for storage, Network for fetch. This module is all about things students can't see, like timers waiting in a queue, strings stored in the browser, and requests in flight. DevTools is how you show them.
  • Blue blocks are concepts, teal blocks are hands-on, and amber blocks are watch-outs: the errors that eat class time if you don't head them off.
  • The quiz answers here are for you. The student workbook has 3 questions from each lesson quiz, without answers, labeled with the lesson's question numbers. The separate Answer Key covers every question, with the same numbers, for grading.
Before you start the module

Students need VS Code with Live Server running. L19's storage and L20's mock fallback both need an http:// origin, not file://. They should be comfortable with querySelector, addEventListener, createElement, and textContent from Module 4. Each lab is a stand-alone folder in labs/module-5/. Hand out the starter folders at the start of the module. If someone falls behind, pair them up. Don't stop the whole room to fix one setup.

L20 needs a plan: GitHub's rate limit

Without logging in, the GitHub API allows about 60 requests per hour per IP address. A classroom behind one shared IP can use that up in minutes, and after that every request comes back 403. Before Day 5, read the L20 lab notes below and labs/module-5/README.md. The solution has a clearly marked USE_MOCK switch that uses mock-user.json instead of GitHub.

By the end, students have four portfolio-ready pages and the tools for the Module 6 capstone.

Lesson Plans

L17

Forms & Validation

55 min
Objectives
  • Read form values with .value / .checked and through form.elements
  • Handle submit with event.preventDefault(); collect data with FormData
  • Write required, length, pattern (regex), and matching-field checks
  • Validate on blur, then re-validate on input once a field is "touched"
  • Show accessible errors (role="alert", text as well as color) and know the Constraint Validation API
  • Explain why the server must validate again
Teaching sequence
  1. Frame (4m). Fill in a sign-up form with a bad email and hit Submit. The page reloads and everything is gone. Ask: "What would a good form have done?" Collect answers: warned me sooner, kept my data, told me what was wrong. That's today's list.
  2. Reading values (6m). Type in an input, then read it in the console: document.querySelector("#username").value. Show that a number input still gives a string, and that a checkbox needs .checked, not .value. Then show form.elements.email.value as the tidy way to reach fields by name.
  3. Submit + preventDefault (7m). Live-write the handler without preventDefault() first, so the console message flashes and disappears on reload. Then add it as the very first line: 
    form.addEventListener("submit", (event) => {
  event.preventDefault();   // first line, always
  const data = Object.fromEntries(new FormData(form));
  console.log(data);
});
    Point out: listen for submit on the form, not click on the button. That way pressing Enter works too.
  4. Validation patterns (8m). Build isRequired, isLengthValid, and the email regex /^[^\s@]+@[^\s@]+\.[^\s@]+$/. Read the regex aloud as "something, @, something, dot, something" and don't turn it into a regex lecture. Add the password-match check. Each validator returns true/false and shows or clears its own message.
  5. Real-time: blur then input (7m). Show the "yelling form" first: validating on every keystroke from the start, so the email field turns red after one letter. Then add a touched Set: blur marks the field touched and validates it, and input only re-validates touched fields. Demo showError/showSuccess with role="alert" on the message span.
  6. Constraint API + the server rule (5m). Quick tour: required/minlength/pattern, input.validity, novalidate, and setCustomValidity("") to clear. Then the most important part: disable JavaScript in DevTools (or point out that anyone can call the endpoint with fetch() from the console) and show that the garbage gets sent without any checks. "Anything in the browser can be bypassed. Client-side validation is for user experience. The server always checks again."
  7. Lab (15m). Launch the registration-form lab (below).
  8. Check + journal (3m). Quick quiz poll, then the journal prompt.
Lab — Registration Form with Real-Time Validation

Students complete TODOs 1–5 in script.js: helpers, four validators, a 0–5 password strength meter, blur-then-input wiring, and a submit handler that hides the form and shows the success message. Starter in labs/module-5/l17-forms-validation/starter/; solution in labs/module-5/l17-forms-validation/solution/. The lesson calls the page registration.html; the lab splits it into index.html + style.css + script.js.

Run these three test cases on your screen and have every student run them too: (1) empty submit: all four errors appear and focus jumps to Username; (2) a weak password like abc: the meter reads "Very weak" and blur shows the length error; (3) type a mismatched confirm, tab out to see "Passwords do not match," then go back and change the password to match. The confirm error should clear on its own. If it doesn't, they're missing the "password changed → re-check confirm" line.

Watch-outs
  • preventDefault() in the wrong place. If a bug throws before it runs, the page reloads and wipes the console, so the error looks like "nothing happens." Put it on line one. Tick Preserve log in the console to catch it.
  • .value is always a string. "25" > "100" is true. Convert with Number() before comparing.
  • Short-circuiting the validators. validateA() && validateB() stops at the first failure, so the other errors never show. The solution uses map() to run them all, then every(Boolean).
  • Duplicate error spans. Creating a new span on every blur stacks messages. Find the existing one first, create only if it's missing, and set textContent (never innerHTML).
  • "My JS validation makes it secure." It doesn't. Repeat the server rule until students can say it back.
Check for understanding

Key answers: read a text input with A) input.value; preventDefault() in submit C) stops the reload/navigation; checkbox state = D) checkbox.checked; blur is for B) validating after the user leaves a field; client-side isn't enough because C) users can bypass it; the stuck custom message = D) never cleared with setCustomValidity("").

L18

Timers & Animation

50 min
Objectives
  • Delay and cancel with setTimeout/clearTimeout; repeat and stop with setInterval/clearInterval
  • Build a countdown; know when recursive setTimeout beats setInterval
  • Tell debounce from throttle
  • Explain the event loop: call stack, microtask queue, task queue
  • Animate with requestAnimationFrame or, better, by toggling a class for a CSS transition
Teaching sequence
  1. Frame (3m). Show the finished Pomodoro timer from labs/module-5/l18-timers-animation/solution/ on the 1-minute preset. "By the end of the hour, you'll have built this."
  2. setTimeout + cancel (6m). setTimeout(showWelcome, 2000), then the classic bug setTimeout(showWelcome(), 2000): it fires immediately. "Parentheses call it now. No parentheses hands it over for later." Store the returned ID and cancel it with clearTimeout.
  3. setInterval + countdown (6m). Live-code startCountdown(10, display) and cancel it with clearInterval when it reaches 0. Draw the recursive-setTimeout comparison: the interval fires on a fixed rhythm, while the recursive timeout waits until each run is done.
  4. Debounce vs throttle (6m). Type into a search box with a plain listener and the console floods. Wrap it in debounce(fn, 300) and the messages come only after typing stops. Compare it to an elevator door that waits for people to stop coming in. Throttle is "at most once every N ms," which suits scroll. Tell them to keep debounce handy: it comes back in L20.
  5. The event loop (7m). Ask the room to predict the output before you run anything. Open labs/module-5/l18-timers-animation/demo/event-loop.html, click Run it, and get A, D, C, B. Walk through the diagram below: sync code runs first, then all microtasks (promises), then one task (timers). Then click the quiz button: sync, promise, timer. Land the takeaway: a timer's delay is a minimum, not a promise. This is also why the stretch timer calculates from Date.now() instead of counting ticks.
  6. rAF + CSS transitions (5m). Show one requestAnimationFrame loop using the timestamp, then the easier approach: CSS defines the transition and JS only toggles a class. Mention prefers-reduced-motion: big motion is something users should be able to opt out of.
  7. Lab (14m). Launch the Pomodoro lab.
  8. Check + journal (3m).
Lab — Pomodoro Timer with Animated Progress

TODOs 1–8: DOM references, state, updateDisplay() (MM:SS with padStart, plus the ring's stroke-dashoffset = CIRCUMFERENCE × (1 − remaining/total), where r = 130 and the circumference is 816.81), start/pause/reset, the 25/15/5/1-min presets, and the bonus colors: red under 30 s, green at 0. Files in labs/module-5/l18-timers-animation/: starter/, solution/ (the lesson's tick-counting version), and stretch/.

Testing tip: nobody should wait 25 minutes. Use the 1-min preset, or type remainingSeconds = 5 in the console before pressing Start. Stretch for fast finishers: the lesson's "Going further." Store endTime = Date.now() + remainingSeconds * 1000 on Start and calculate Math.ceil((endTime - Date.now()) / 1000) on each tick. Then switch tabs for 30 s and compare the two versions. Also add a prefers-reduced-motion rule that turns off the ring transition. Reference: stretch/.

Watch-outs
  • Double-click Start = double speed. Each click starts another interval, and the timer runs 2× fast and can't be paused. The if (isRunning) return; guard fixes it. Let a student find this bug. It teaches more than any slide.
  • Lost interval ID. const intervalId = setInterval(...) declared inside start() can't be reached by pause(). State lives outside the functions.
  • Calling instead of passing: addEventListener("click", start()) runs start once, at load.
  • The ring goes the wrong way or doesn't move. Check that stroke-dasharray is 816.81 and the formula is 1 − remaining/total. The SVG is rotated −90° so the ring starts at 12 o'clock.
Check for understanding

Key answers: setTimeout returns D) a numeric timer ID for clearTimeout(); A / timeout B / C logs B) A, C, B; interval vs recursive timeout = C) interval fires regardless; recursive waits for completion; rAF because A) it syncs with the display and pauses in background tabs; debouncing = D) delay until events stop, resetting on each event; timer/promise/sync logs B) sync, promise, timer.

L19

Local Storage

45 min
Objectives
  • Use setItem, getItem, removeItem, clear
  • Store arrays and objects with JSON.stringify / JSON.parse, with a safe fallback
  • Choose between localStorage and sessionStorage
  • Apply the load → render → update → save pattern; know the storage event
  • Know the limits (~5 MB, synchronous) and never store secrets
Teaching sequence
  1. Frame (3m). Add three tasks to a plain to-do list, then refresh the page, and they're gone. "Everything we've built so far forgets on refresh. Today it starts remembering."
  2. The four methods + DevTools (6m). Split the screen: console on one side, Application → Local Storage on the other. setItem("theme", "dark") and watch the row appear. getItem on a missing key gives null. Then setItem("score", 42) and typeof getItem("score") gives "string".
  3. The JSON round-trip (7m). setItem("user", {name: "Ray"}) stores "[object Object]". Show it in DevTools, because the reveal matters. Then show the fix: JSON.stringify on the way in, JSON.parse on the way out, and the loadData(key, fallback) helper with try/catch. Corrupt the value by hand in DevTools and reload to show why the catch matters.
  4. session vs local (4m). Same API, different lifetime. Open a second tab: localStorage is shared across tabs and sessionStorage is not. Quick rule: "Would the user expect it tomorrow? Use local."
  5. State-sync pattern + storage event (5m). Write the pattern on the board: load once → render → on every change: update the array, save, render. The array is the truth, and the page is drawn from it. Mention the storage event: it fires in the other tabs, never in the one that made the change.
  6. Limits & security (4m). About 5 MB, synchronous, QuotaExceededError. Then the rule: any script on the page can read storage, so never store passwords or tokens there. HttpOnly cookies are the answer for auth.
  7. Lab (13m). Launch the to-do lab.
  8. Check + journal (3m).
Lab — Persistent To-Do List

Seven TODOs: 1 loadTodos/saveTodos (try/catch, [] fallback) · 2 render (empty state; checkbox, span.todo-text, button.delete-btn) · 3 addTodo · 4 toggleTodo/deleteTodo · 5 updateCount · 6 listeners, with event delegation on the <ul> · 7 load and render on start. Files in labs/module-5/l19-local-storage/.

Accessibility check: without an accessible name, a screen reader announces the checkbox and the × button as just "checkbox" and "times." The lesson and the lab solution both add aria-labels (Mark "Buy milk" as done, Delete "Buy milk"), a visually-hidden <label> for the input, and puts focus back after render() rebuilds the list. Show this at the end of the lab as the "production polish" step. Success check: add two tasks, tick one, refresh, and everything is still there.

Watch-outs
  • Forgetting to save. The list works until refresh, then comes back stale. Every function that changes todos must call saveTodos.
  • ID type mismatch. li.dataset.id is a string and todo.id is a number, so === never matches and toggle/delete silently do nothing. The fix is Number(li.dataset.id).
  • Listeners on each item instead of delegation. They vanish every time render() clears the list. One listener on the <ul> + closest(".todo-item") handles everything.
  • Shared origin in class. Every student project on 127.0.0.1:5500 shares the same todos key. Old demo data can show up in a new project. Teach localStorage.removeItem("todos").
  • innerHTML with task text. Always use textContent. Have someone add the task <b>hi</b> to prove it shows as plain text.
Check for understanding

Key answers: missing key returns B) null; storing an object directly gives D) "[object Object]"; store an array with A) JSON.stringify(myArray); sessionStorage C) clears when the tab closes; no tokens because C) any JS on the page can read it (XSS); the storage event fires B) in the other tabs, not Tab A.

L20

Working with APIs & Fetch

60 min
Objectives
  • Explain APIs, endpoints, REST methods, and JSON
  • Describe a Promise's three states; chain .then()/.catch()
  • Use fetch(), check response.ok, parse with response.json()
  • Rewrite with async/await + try/catch; run requests in parallel with Promise.all
  • Show loading, data, and error states safely (escape or textContent)
Teaching sequence
  1. Frame (4m). Paste https://api.github.com/users/octocat into the browser address bar, and raw JSON appears. "That's an API. Today your page asks for this and turns it into a profile card."
  2. APIs, REST, JSON (5m). Request → endpoint → response. Keep the GET/POST/PUT/DELETE table short: today is almost all GET.
  3. Promises (8m). Use the restaurant-buzzer analogy: you get the buzzer (the Promise) right away and the food (the value) later. Three states: pending, fulfilled, rejected. Live-code the .then().then().catch().finally() chain against JSONPlaceholder, then remove a return to show the next .then receiving undefined.
  4. fetch + response.ok (8m). Fetch /users/9999 from JSONPlaceholder. It's a 404, but the .then still runs. This is the big surprise: fetch only rejects for network failures. Add if (!response.ok) throw …. Open the Network tab and show the request, its status, and its response body. Use the diagram below.
  5. async/await + try/catch (8m). Rewrite the same request with async/await, side by side with the .then version. Point out that await only works inside an async function (or a module). Show Promise.all: the total time is the slowest request, not the sum of all of them.
  6. Displaying data (6m). Loading → data | error. Render with createElement + textContent, and show escapeHTML for when you must use a template string. Briefly mention CORS: the fix is on the server, not in your code.
  7. Lab (18m). Launch GitHub User Search, using the rate-limit plan below.
  8. Check + journal (3m).
Lab — GitHub User Search

TODOs 1–7: DOM references; showLoading/showError/showUser (avatar, name, @login, bio, repos/followers/following, all as text); async searchUser with separate branches for 404, 403/429 (rate limit), other statuses, and a catch for network errors; click + Enter; bonus debounce and profile link. Files in labs/module-5/l20-apis-fetch/.

Rate-limit plan (60 requests/hour per IP, and the room shares one IP): (1) pair up. One laptop searches while the partner reads the code and predicts the branch. (2) No auto-search in class: debounced search-as-you-type spends a request on every pause. It's off (AUTO_SEARCH = false) in the solution, so demo it once and turn it off again. (3) Test 404 with one made-up name rather than many. (4) When the room hits 403, switch to the fallback: open the solution as index.html?mock or set USE_MOCK = true. In mock mode, octocat returns the sample profile from mock-user.json, ratelimit simulates a 403, and any other name simulates a 404. Students can point their own fetch at mock-user.json; the starter's top comment explains how. Treat the 403 as a teaching moment: this is the error branch they just wrote, working.

Watch-outs
  • Forgetting await. const user = response.json() logs Promise {<pending>} and every field is undefined. When you see "Promise" in the console, look for a missing await.
  • Expecting 404 in catch. It never gets there. Branch on response.status/response.ok before parsing.
  • Raw API text in innerHTML. Bios are user-written. Use textContent, or escapeHTML when you use a template.
  • Double requests. Enter + a debounced input listener both fire, which burns quota twice as fast.
  • file:// URLs. Some browsers block or restrict requests from file:// pages, and the mock JSON won't load. Use Live Server.
Discussion (5 min, if time allows): the stale-response race

With debounced search, a student types oc, pauses, then finishes octocat. Two requests are now in flight. If the oc answer comes back last, it overwrites the right result. Ask: "The responses came back in a different order than we sent them. How do we make sure only the newest search wins?" Take ideas, then show the solution's guard: a latestSearch counter, where each search remembers its own number and returns early after every await if a newer search has started. (AbortController is the more advanced tool. Mention it by name only.)

Check for understanding

Key answers: fetch() returns B) a Promise that resolves to a Response; on 404 A) the Promise resolves with ok = false; async C) always returns a Promise and enables await; Promise.all because B) parallel: total = slowest, not the sum; the three UI states = D) loading, data, error; the CORS error = C) the server didn't allow your origin.

Closing the Module

Module 5 wrap-up (10 min)

Ask for one volunteer per app to demo: the form catching a bad email, the timer turning red, the to-do list surviving a refresh, and the search finding a real profile (or the mock one). Recap the arc: capture input → act over time → remember → talk to the world. Then name the pattern they used four times: state → render → events → update. Preview Module 6: "You now have every tool you need. Next you put them together into a capstone app of your own."
