Building a Complete Project

90 min
By the end you can
  • Plan an app first: features, a data model, and how the parts connect
  • Keep a data layer (create, read, update, delete + localStorage) separate from rendering
  • Use one form for creating and editing, with validation
  • Add debounced search, a filter, a fetched quote with a fallback, and keyboard shortcuts
  • Put user text on the page safely with textContent
Key ideas — one loop runs the whole app
  • Plan before you code. A feature list, the shape of one note object, and the loop above save hours of rework.
  • The data layer (loadNotes, saveNotes, createNote, updateNote, deleteNote, getNotes) knows nothing about the DOM. renderNotes() rebuilds the grid from the data every time.
  • One form, two modes: an empty hidden #note-id means "create"; an id means "edit."
  • Event delegation: the cards are rebuilt on every render, so one click listener on #notes-grid handles every ✏️ and 🗑️.
  • Graceful degradation: if the quote API fails, show a fallback and keep going. Everything the user typed goes in with textContent.
Worked example — one form, two modes
noteForm.addEventListener("submit", (event) => {
    event.preventDefault();
    if (!validateForm()) return;
    const editId = noteIdInput.value;          // "" or "1713300000000"
    if (editId) {
        updateNote(Number(editId), titleInput.value, bodyInput.value, categorySelect.value);
        showSaveStatus("Note updated!");
    } else {
        createNote(titleInput.value, bodyInput.value, categorySelect.value);
        showSaveStatus("Note saved!");
    }
    hideForm();
    renderNotes(searchInput.value, filterCategory.value);
});

Read it as the loop: the submit is the user action; createNote/updateNote update state and save; renderNotes re-renders. Number() is needed because input values are always strings.

Next Steps & Best Practices

45 min
By the end you can
  • Read an error message for what went wrong and where
  • Debug with console.table, debugger and breakpoints, one hypothesis at a time
  • Organize code by concern with clear names and small functions
  • Spot the common pitfalls and read modern syntax like ?. and ??
  • Choose what to learn and build next
Key ideas — debug with a loop, not with luck
Error says…Usually meansTry
Cannot read properties of nullquerySelector returned nullCheck the selector; does the element exist yet?
X is not a functionCalling something that isn't a functionCheck spelling, import, variable type
X is not definedThe variable doesn't exist in this scopeCheck spelling, scope, declaration order
Unexpected tokenSyntax error (missing bracket, comma)Check the line before the error line
Cannot read properties of undefinedA nested property's parent is missingLog the data's shape; use ?.
  • debugger; only pauses when DevTools is open. Or click a line number in Sources to set a breakpoint.
  • Pitfalls: queries can return null · fetch isn't finished on the next line · use === · spread copies are shallow (structuredClone is deep) · add delegated listeners once · test the edge cases (empty, zero, offline, first visit).
  • ?? falls back only for null/undefined; || also replaces 0, "" and false.
  • Organize by concern (data · rendering · events), name things for what they do, keep functions small. Split big projects into modules with <script type="module">; they need a server like Live Server.
Worked example — reading an error
// Uncaught TypeError: Cannot read properties of null (reading 'textContent')
//     at renderUser (app.js:45:23)

// WHAT:  reading .textContent on something that's null
// WHERE: app.js line 45, inside renderUser
// WHY:   querySelector probably found nothing
const el = document.querySelector("#user-name");
if (el) el.textContent = name;           // or: check the selector!
